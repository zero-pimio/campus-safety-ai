# 人员门禁通行事件规格 v1

状态：设计待实现。本文描述拟新增的人员门禁规则，不表示当前代码已接入门禁控制器、完成实景验证或生成演示视频。

共享术语、输入契约与判定账本以 [访问通道设计](../design/access-control-v1.md) 为准。本文使用 `GateSignal`、`PassageAssessment`、`passageId` 和四种 `outcome`：`authorized`、`unauthorized`、`uncertain`、`not_required`。拟新增确定事件类型为 `pedestrian_access_violation`；现有 `intrusion` 继续表示禁区内的人员进入事件，不承担刷卡授权判断。

## 1. 目标与范围

将同一固定摄像头源周期内的人员完整穿越，与对应通道、方向和时间范围内的权威门禁信号关联，输出可复核的通行判定。覆盖未经授权穿越、受限方向逆行、满足证据条件的尾随，以及合法通行和无法判断的情形。

- 不做人脸身份识别，不根据外观或轨迹确定现实中的姓名、学号、持卡人身份。
- `trackKey` 只关联同一视频源周期内的画面目标；`passageId` 标识一次通行实例，两者均不是人员身份。
- 不从视频读取或猜测完整凭证号码；门禁凭证仅保留必要的不透明引用。
- 不支持跨摄像头身份接续，不通过事件分析自动开门、锁门或阻断出口。
- 本规则依赖授权与运行模式的可信输入。纯视频模式可以形成穿越事实及复核线索，不能据此确认“没有授权”。

## 2. 场景标定与运行前提

每个通道使用共享契约中的稳定 `gateId` 与 `laneId` 组合，标定 A 侧等待区、门槛或过渡区、B 侧完成区，注明两个方向分别对应进入还是离开。标定还要包含读卡器所属侧、有效通道范围及可见性适用条件；邻近门口、旁边队列和相邻读卡器不能共用未区分的授权池。

完整穿越是可信连续观测支持的 A→过渡区→B，或 B→过渡区→A，并满足终点侧稳定确认要求。方向按区域顺序判断，不能只看人体朝向、一个检测框的位置或一条线上的抖动。快速穿越也有效，不沿用当前禁区规则“在区域内停留 2 秒才开始”的条件。

上线前必须用现场数据冻结并版本化以下参数，本文不以示例默认值代替现场验证：

| 配置项 | 必须确定的语义 |
| --- | --- |
| 允许方向与授权要求 | 按方向、时段和运行模式定义；进入与离开可不同 |
| 完整穿越条件 | 起点、过渡区、终点的顺序、稳定时间及几何滞回 |
| 最大观测间隔 | 超过后不把缺失区间当连续移动或完整穿越 |
| 授权有效窗口 | 生效、失效、撤销及已使用状态的解释 |
| 时钟与迟到界限 | 视频和控制器时间偏差、不确定范围、可等待的日志迟到窗口 |
| 通行容量 | 单人、多人、护送、儿童及陪护的现场计数政策 |
| 额度消费规则 | 由实际控制器协议确定消费触发点、预留、退款和重复日志处理 |
| 运行模式优先级 | 应急、自由通行、人工放行、维护和普通受控模式的有效范围 |

缺少必需配置或处于验证范围之外时，应输出具体的不可判定原因，不自动套用“一证一人”。

## 3. `GateSignal` 的业务解释

`GateSignal` 将门禁控制器的原始事件转换为共享设计中的规范信号。实现时须保留来源引用、事件时间、接收时间、序号或去重标识，并能够说明对应窗口是否完整；本文不另建与共享设计冲突的字段表。

| 观测或信号 | 可以证明 | 不能单独证明 |
| --- | --- | --- |
| 刷卡尝试 | 发生过认证请求 | 认证通过或已获通行授权 |
| 认证成功 | 控制器接受了该认证结果 | 此方向已获通行额度、画面中的某人就是持卡人 |
| 通行批准 | 指定通道、方向、有效期与容量的授权 | 某个轨迹必然拥有该授权、实际已完成穿越 |
| 拒绝或撤销 | 某次请求失败或某项授权被撤销 | 随后所有穿越都无其他合法授权 |
| 门锁释放、门开启 | 物理动作或状态 | 任意人数可自由进入 |
| 自由通行或应急模式 | 有效范围内无需普通刷卡授权 | 另一方向、另一通道或另一时间也自由通行 |
| 控制器心跳正常 | 当前通信有响应 | 历史窗口没有丢失事件 |

运行模式按可信来源的生效时间与范围判断。画面中的门一直开着不能替代自由通行信号；定时开放、管理人员批准、护送和消防释放也不能被普通刷卡记录的缺失覆盖。模式信号矛盾、缺失或时间无法对齐时，保留 `uncertain`。

## 4. 通行实例与授权关联

通行实例使用共享状态 `approaching → crossing → completed / aborted / unknown`，区分靠近、穿越中、完整穿越、中途返回和无法确认的结果。只有完整可靠的穿越才进入确定违规事件的投影条件。授权核对的 `pending` 是持久化 episode 的处理状态，不是第五种 `outcome`，不能预先填为 `unauthorized`。

1. 建立通行实例时分配稳定 `passageId`。同一完整穿越中的短暂遮挡、检测抖动、可解释的轨迹切分不能重复计数；不能仅靠新出现的轨迹 ID 认定新增人员。
2. 依据通道、方向、有效时间和控制器规则建立授权候选集。视频采集时间与控制器事件时间经过受控对齐，保留误差范围；不能只按接收时间或“最近一次刷卡”绑定。
3. 有充分依据时才将授权容量分配给该次通行。多个候选同样合理时保留歧义，不能为了消耗额度任意指定持卡轨迹。容量型政策可以在受约束的完整通行组上核对覆盖，但不能把总数相等代替通道、方向、时间、类别与对象约束检查。
4. 额度消费时点必须按实际控制器规则冻结并写入版本配置。不能因检测到框、开始跟踪或靠近读卡器擅自扣减。若实际协议明确规定进入边界或控制器确认即消费，则可以早于完整穿越消费；这不是违规事件已经成立，仍要等待完整穿越后判定。
5. 若采用内部预留，预留应可追踪；中止、取消或过期时只能按规则释放尚未消费的预留。已消费额度不能因返回、视频未见完整通过、断流或重启而自动退还；视频通行状态与授权消费事实独立持久化，不能为后来者复活旧额度。
6. 完整穿越后，在有限等待窗口内核对授权与完整性水位，形成 `PassageAssessment`。等待截止而完整性仍无保障时也必须形成 `uncertain` 记录，不能一直挂起或默认无授权；普通在线心跳不代替覆盖水位。消费与通行状态的持久化不等待完整穿越或最终判定。

授权关联仅表示该通行在现有政策下被额度覆盖。若政策仅要求容量覆盖，且完整通行组中各次穿越均满足授权适用范围，可以输出 `authorized` 并保留无法唯一配对的授权候选，不声称识别了每个持卡人或掌握精确的一一消费关系；组内占用容量仍须防止再次分配。若政策要求绑定具体对象，而关系无法确定，则即使总人数与授权数相等也必须 `uncertain`。

## 5. 判定与违规原因

四种 `outcome` 表示判定结论，不复用 `EventRecord.status` 或 `confidence` 表达。

| `outcome` | 判定要求 | 交付方式 |
| --- | --- | --- |
| `authorized` | 完整穿越被有效授权及现场容量政策覆盖，方向政策与必要关联条件均满足 | 通行审计，不产生确定违规事件 |
| `not_required` | 穿越方向及时间处于可信的自由通行、应急或其他无需授权模式，且不违反适用方向政策 | 通行审计，不产生确定违规事件 |
| `unauthorized` | 完整穿越可信，适用政策明确，必要控制器证据完整且时间可信，并有足够依据确认违反授权或方向规则 | 可投影为 `pedestrian_access_violation` |
| `uncertain` | 穿越、授权关联、计数、模式、日志覆盖或时间关系任一关键事实不足 | 独立判定账本与复核记录，不冒充确定违规 |

### 未经授权穿越

在该方向要求授权时，确认完整穿越，并确认没有可分配的有效授权容量或相关授权已失效，同时排除自由通行、人工放行、护送和其他合法政策。没有接入日志、日志缺口、未知序号丢失或控制器重启造成覆盖不明，都不是“无授权”的充分证据。

刷卡失败但没有穿越，不生成闯门事件；刷卡失败后另获有效授权再穿越，也不能仅凭前一条拒绝信号报警。

### 尾随

尾随是未经授权穿越的一种有额外证据要求的原因。不能仅凭“刷 1 卡、看见 2 个框或 2 条轨迹”确认。

确认具体尾随通行，至少同时满足：

- 该次释放对应的容量与消费规则明确，例如经现场确认的单人授权。
- 存在可区分、可靠计数的独立完整穿越，连续性与可见性足以排除重复检测、轨迹切分和对象混淆。
- 前一通行与授权的关联及额度消耗有足够依据，后一通行利用同一释放窗口沿受控方向完成穿越。
- 覆盖相关时间范围的权威日志完整、时间可信，后一通行没有独立有效授权，也不属于护送、多人成组许可或自由通行。
- 可以可靠地将不被授权覆盖的通行与相应 `passageId` 关联，而非任意把第二个框指定为违规者。

若只能证明窗口内完成的总通行数超过总授权容量，但不能确定哪次通行无授权，应记录通道层容量不匹配线索，并将无法判定的通行保留为 `uncertain`。不得把群体计数差异直接分配给某个轨迹，生成针对它的确定尾随事件。

### 逆行

逆行指完整穿越方向违反当时生效的方向政策，不以人员朝向或门外走动方向判断。有剩余授权容量也不能自动覆盖禁止方向；可信的方向例外、人工批准或应急模式是否允许该方向，须先依有效政策核对。通行方向合法的自由出口或应急疏散不是逆行。进入过渡区再回到原侧属于中途返回；已完整穿越后再完整返回则是两次通行，分别判断其方向和权限。

同一次通行同时违反方向和授权要求时，共享一个 `passageId`，在独立判定账本记录原因；不要生成互相重复的“闯门、尾随、逆行”告警。

## 6. 必须处理的边界情形

| 情形 | 处理要求 |
| --- | --- |
| 正常刷卡并通过 | 有效授权覆盖完整穿越，`authorized` |
| 成功刷卡但一直未过门 | 记录未完成通行与授权到期；不生成闯门；不擅自退回控制器已消费额度 |
| 进入过渡区后退回原侧 | 中止通行；不能当作完成入门、逆行或第二人尾随 |
| 完整进入后又完整出来 | 两次方向明确的通行；返回不自动撤销第一项事实或恢复额度 |
| 一张单人授权、两次清晰完整通行 | 满足尾随的全部证据条件后，才可确认相应违规通行 |
| 两张有效授权、两人紧跟 | 容量与必要关联均满足时合法；间距小不是尾随依据 |
| 一张允许两人的授权 | 按容量政策判断，不能固化为一证一人 |
| 合法护送或轮椅陪护 | 依据明确的护送范围与容量；不得以两个目标框否定合法政策 |
| 成人抱孩子、推婴儿车 | 应有明确计数及儿童政策；无法区分人数或政策缺失时 `uncertain` |
| 推箱子、行李车、反射或海报 | 不得把非人员对象、反射或静态形象计作新增通行者 |
| 两人遮挡成一人，再分离为两条轨迹 | 不按 ID 数量补计人数；完整通行人数无法恢复时 `uncertain` |
| 两人排队、刷卡位置被挡或同时双向通过 | 保留授权候选歧义；不能强行绑定最近的人 |
| 门长时间开着但进入仍需授权 | 物理开启不免除授权要求，继续按有效政策判断 |
| 定时开放或合法人工放行 | 在可信生效范围内记录相应合法依据，不因没有刷卡误报 |
| 自由出口或消防应急疏散 | 生效方向内 `not_required`，不产生未刷卡或尾随告警 |
| 模式在穿越期间切换 | 依据冻结的生效时间与过渡政策；边界无法确定时 `uncertain` |
| 授权日志迟到但在容许窗口内 | 等待对账后定案，不先发布确定违规再静默改写 |
| 日志缺口、时钟偏差超界或控制器重启 | `uncertain`，标明具体原因；恢复通信不补造历史完整性 |
| 视频开始时目标已在门中 | 起点未知，不能补猜完整穿越 |
| 穿越期间断流、长遮挡或源周期切换 | 未确认的穿越收口为不确定；不能跨周期拼接轨迹 |

## 7. 判定账本与事件生命周期

`PassageAssessment` 是独立的判定账本记录，以 `passageId` 关联穿越事实、授权引用、适用模式/策略版本、结论及其理由和证据。其版本、纠正与来源引用遵循共享设计。后到证据改变结论时，保留原判定并追加可追溯的更正记录，不覆盖历史。

现有 `EventRecord` v1 保持原契约，不新增 `details`，不虚构 `retract` 阶段，不把业务判定塞入 `status`，也不把视觉检测分数当成“未授权的概率”。通道、控制器覆盖、关联歧义、收口原因和更正关系保存在独立账本中。事件和判定之间的引用关系也由独立账本保存。

确定事件的生命周期如下：

1. 候选、未完成通行和 `uncertain` 结论不发布确定违规 `START`。
2. 完整可靠穿越并得到 `unauthorized` 判定后，才以 `pedestrian_access_violation` 发布 `START`，保持稳定事件标识和原始通行时间依据。
3. 单次通行是短事件，可随后有序发布 `END`；不等待目标长时间滞留或走出整幅画面。`END/CLOSED` 表示记录收口，不表示人员安全、违规消失或撤销原结论。
4. 若结束前需要补充材料，按单调 revision 发布允许的 `UPDATE`；所有记录继续使用 `eventId:revision` 幂等键。不得依赖当前契约未提供的事件撤回机制。
5. 已经结束的事件因迟到日志或人工复核需要更正时，只在独立判定账本追加不可变更正版本及对原事件的引用，进入本地复核；不发 END 后 UPDATE，不改已交付载荷，不重开已关闭事件。当前路径不保证平台展示更正或撤回告警；平台更正须另行明确协议并实测，不能将本地更正记账说成平台告警已经撤销。
6. 断流、重启、回放结束或源周期切换必须终结暂态通行，并收口已打开事件。已经确认的事实不能因断流变成“未发生”；尚未确认的事实不能在收口时升级为确定事件。

去重针对同一次通行及其事件版本。不能直接沿用禁区事件按同一轨迹设置的长冷却时间，吞掉该目标随后真实完成的另一项通行；也不能因轨迹切分把一次通行拆成多个告警。源周期隔离、单调时间和重复输入处理继续遵循当前项目约定。

## 8. 数据、证据与回放包

人员门禁回放包至少包含：

- 能覆盖靠近、读卡区域、过渡区与完成侧的原始录像及可靠采集时间；明确不可见区域和超出适用范围的片段。
- 固定检测或轨迹观测、通道标定、策略配置及对应版本，注明源周期边界。
- 控制器原始日志和规范化 `GateSignal`，包括授权、拒绝、撤销、门状态、运行模式、序号连续性与缺口。
- 控制器与视频的时钟偏移、误差范围和日志迟到信息，避免回放中假定完美同步。
- 人工标注的完整通行、方向、中途返回、可见性、可判定人数，以及能够依据日志确认的授权关系和不确定原因。
- 期望 `PassageAssessment`、期望事件生命周期和判定更正；包含输入重复、乱序、迟到与重连反例。

事件证据应能复核穿越前后及对应门禁依据。至少提供带时间和通道标记的短视频、关键截图、通行与授权时间线及证据可用性状态。截图不能独自证明尾随；证据中应区分模型框、轨迹、授权引用和最终判定，避免将可视化标签表述为身份识别结果。

证据生成失败不能静默丢弃已经成立的安全事实，应在账本或证据清单中记录失败和可用性缺陷。录像、标注、模型训练集和交付演示的用途应分别登记，测试或演示输入不得冒充实景效果验证。

## 9. 验收与视频演示

模块完成时必须交付可播放的演示视频，并实际打开播放、检查画面和声音轨道（如有），确认字幕、判定与事件收口一致。脚本通过、截图、日志文件或一个视频路径均不能代替视频交付。当前仍为设计阶段，以下条目均待实现和演示，不代表已有产物。

可以采用一个带章节的视频或多个独立片段。每段须标明使用真实控制器、录制日志还是模拟信号；模拟演示只能验证规则链路，不可宣称门禁实机已验收。视频叠加展示通道与方向、脱敏授权/容量、适用模式、`passageId`、`outcome`、判定原因以及事件 `START/END`；看得清穿越和信号时序，不在画面中显示身份推断。

| 必须演示的章节 | 输入与画面要求 | 期望判定与事件 |
| --- | --- | --- |
| 正常刷卡 | 一份有效授权，一人完整通过 | `authorized`，无确定违规事件 |
| 一证两人 | 经确认的单人容量，两个清晰完整穿越，日志完整且关联明确 | 对确有证据的未授权通行给出 `unauthorized`，展示尾随理由及唯一事件的 `START → END` |
| 两证两人 | 两份有效授权，两人紧跟通过 | 容量及必要关联满足时 `authorized`；不能因距离近误报 |
| 合法护送 | 明确允许的双人或护送授权，两人完整通过 | `authorized`，显示护送或容量依据 |
| 应急自由出口 | 可信应急/自由出口模式及正确方向，无刷卡通过 | `not_required`，无未授权或尾随告警 |
| 日志缺口 | 穿越清晰，但授权日志人为缺段或完整性未知 | `uncertain`，展示缺口理由和复核入口；不发布确定违规 |
| 刷卡未过与中途返回 | 成功刷卡未穿越；另展示进入过渡区后退回原侧 | 无确定违规事件，不凭框数消费额度；按实际控制器规则解释授权状态 |
| 方向违规 | 明确单向受控政策下，清晰完成反向穿越 | 证据完备时 `unauthorized`，同一次通行只有一个事件 |
| 遮挡与计数歧义 | 双人重叠、轨迹切分或抱孩子等无法可靠计数的片段 | `uncertain` 或按已验证政策处理；不得强行确认尾随 |
| 事件结束与重连 | 展示已确认短事件的有序结束，再展示穿越中断流或源周期切换 | 已确认事件正常收口；未确认通行保留不确定；无遗留 OPEN、跨周期续接或重复告警 |

演示之外还须完成可复现回放验收：

- 本文合法与歧义反例不得产生错误的确定违规事件；重复帧、重复信号和重试投递不产生重复事件。
- 分别报告完整穿越计数与方向正确性、授权关联正确性、违规事件误报/漏报、每千次通行误报、判定延迟和未知比例。
- 同时公布可判定覆盖率及其可见性、人数和控制器日志条件；不能靠把困难样本全部归为未知而只报告高准确率。
- 训练、调参与验收片段按场景和连续录像隔离，避免同一通行的相邻帧同时进入开发与验收集合。
- 实景性能目标、样本量及容许误报/漏报水平须经现场试点后冻结。未取得实景对齐日志和标注数据之前，不宣称已经达到部署精度。

只有实现、回放结果、证据文件、可播放演示视频及其播放检查全部完成，才能将本模块从“设计待实现”更新为对应已验证阶段；模拟验证与实机验证状态必须分别记录。
